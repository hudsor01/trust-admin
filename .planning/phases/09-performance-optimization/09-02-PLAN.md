## Context

**Current problem**: Multiple components mounting simultaneously trigger duplicate requests
- Example: Two components both call `useEntities()` on page load
- Result: Two identical GET /api/entities requests
- Observable in Network tab: duplicate concurrent requests

**Solution**: Simple in-memory cache with request deduplication
- Deduplicate concurrent requests (same key = single request, shared promise)
- Short-lived cache (30 seconds) to prevent stale data
- No persistence (in-memory only, clears on page refresh)
- Keep it simple: No React Query or SWR (stick to current architecture)

## Tasks

### Task 1: Create request deduplication cache

Add simple cache above the `useQuery` hook:

```typescript
// src/hooks/use-query.ts

interface CacheEntry<T> {
  data: T
  timestamp: number
  promise?: Promise<T>  // For deduplicating concurrent requests
}

const cache = new Map<string, CacheEntry<any>>()
const CACHE_TTL = 30000 // 30 seconds

function getCacheKey(url: string, options?: string): string {
  return options ? `${url}::${options}` : url
}

function getCachedData<T>(key: string): T | null {
  const entry = cache.get(key)
  if (!entry) return null

  const age = Date.now() - entry.timestamp
  if (age > CACHE_TTL) {
    cache.delete(key)
    return null
  }

  return entry.data
}

function setCachedData<T>(key: string, data: T): void {
  cache.set(key, {
    data,
    timestamp: Date.now(),
  })
}

function getOrCreatePromise<T>(
  key: string,
  fetcher: () => Promise<T>
): Promise<T> {
  const entry = cache.get(key)

  // If there's a pending promise, return it (deduplication)
  if (entry?.promise) {
    return entry.promise
  }

  // Create new promise
  const promise = fetcher().then(
    (data) => {
      // Store result in cache
      setCachedData(key, data)
      // Clear promise from cache entry
      const entry = cache.get(key)
      if (entry) {
        delete entry.promise
      }
      return data
    },
    (error) => {
      // On error, remove promise so next attempt can retry
      cache.delete(key)
      throw error
    }
  )

  // Store promise for deduplication
  cache.set(key, {
    data: null as any,
    timestamp: Date.now(),
    promise,
  })

  return promise
}
```

**Commit**: None (utilities only)

### Task 2: Update useQuery hook to use cache

Modify the `useQuery` hook to check cache before fetching:

```typescript
export function useQuery<T>(url: string, options?: { enabled?: boolean }) {
  const [data, setData] = useState<T | null>(null)
  const [loading, setLoading] = useState(true)
  const [error, setError] = useState<Error | null>(null)

  const enabled = options?.enabled ?? true

  useEffect(() => {
    if (!enabled) {
      setLoading(false)
      return
    }

    const cacheKey = getCacheKey(url)

    // Check cache first
    const cachedData = getCachedData<T>(cacheKey)
    if (cachedData) {
      setData(cachedData)
      setLoading(false)
      return
    }

    // Fetch with deduplication
    setLoading(true)
    getOrCreatePromise(cacheKey, () =>
      fetch(url).then((res) => {
        if (!res.ok) {
          throw new Error(`HTTP ${res.status}`)
        }
        return res.json()
      })
    )
      .then((result) => {
        setData(result)
        setError(null)
      })
      .catch((err) => {
        setError(err)
        toast.error(`Failed to load data: ${err.message}`)
      })
      .finally(() => {
        setLoading(false)
      })
  }, [url, enabled])

  return { data, loading, error }
}
```

**Important**:
- Check cache before setting loading state
- Use `getOrCreatePromise` to deduplicate concurrent requests
- Cache key includes URL (and could include query params if needed)

### Task 3: Add cache invalidation function

Export function to manually invalidate cache when data changes:

```typescript
/**
 * Invalidate cached data for a URL pattern
 * Use after mutations to ensure fresh data on next fetch
 */
export function invalidateCache(urlPattern?: string): void {
  if (!urlPattern) {
    // Clear entire cache
    cache.clear()
    return
  }

  // Clear matching entries
  for (const [key] of cache) {
    if (key.startsWith(urlPattern)) {
      cache.delete(key)
    }
  }
}
```

Usage in mutation hooks:

```typescript
// Example: After creating an entity
const { mutate: createEntity } = useMutation({
  onSuccess: () => {
    invalidateCache('/api/entities')
  }
})
```

### Task 5: Update mutation hooks to invalidate cache

Update `useMutation` hook to invalidate cache on success:

```typescript
// src/hooks/use-query.ts

export function useMutation<T, TVariables = any>(options: {
  mutationFn: (variables: TVariables) => Promise<T>
  onSuccess?: (data: T) => void
  invalidatePattern?: string  // Optional: URL pattern to invalidate
}) {
  const [loading, setLoading] = useState(false)
  const [error, setError] = useState<Error | null>(null)

  const mutate = async (variables: TVariables) => {
    setLoading(true)
    setError(null)

    try {
      const result = await options.mutationFn(variables)

      // Invalidate cache if pattern provided
      if (options.invalidatePattern) {
        invalidateCache(options.invalidatePattern)
      }

      if (options.onSuccess) {
        options.onSuccess(result)
      }

      return result
    } catch (err) {
      const error = err instanceof Error ? err : new Error(String(err))
      setError(error)
      toast.error(`Operation failed: ${error.message}`)
      throw error
    } finally {
      setLoading(false)
    }
  }

  return { mutate, loading, error }
}
```

**Success criteria**:
- Mutations can specify invalidation pattern
- Cache cleared after successful mutations

**Commit**: `feat(09-02): auto-invalidate cache after mutations`

## Notes

**Why not React Query or SWR?**
- Current architecture uses custom hooks
- Simple deduplication sufficient for trust admin use case
- Avoids large dependency (React Query is 42KB gzipped)
- Can migrate to React Query later if needed (Phase 10+)

**Cache Strategy**:
- In-memory only (no persistence)
- Short TTL (30 seconds) to prevent stale data
- Manual invalidation after mutations
- Simple and predictable

**Limitations**:
- No background refetching
- No retry logic
- No optimistic updates
- Sufficient for current needs, can enhance later if required
