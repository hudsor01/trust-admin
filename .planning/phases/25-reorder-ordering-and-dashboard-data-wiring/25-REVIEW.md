## Summary

Phase 25 wires three workstreams: persisted reorder `ORDER BY` on `trustee.list` / `beneficiary.list` / `getBeneficiariesWithDistributions`, a new `dashboard.activityCounts` query feeding the `/accounts` sparkline, and `@next/bundle-analyzer` in `next.config.ts`.

Overall the work is solid. The reorder changes correctly target the schema-defined composite indexes (`idx_trustee_entity_order`, `idx_beneficiary_entity_sort`) with the right column and direction, and the redundant client `.sort()` was removed cleanly with no remaining consumer dependency. The `next.config.ts` wrapper composition is correct. `dashboard.activityCounts` has a genuinely sound security posture: it is `adminProcedure`-gated, `tableName` is a true `z.enum` allowlist mapped to Drizzle table objects via a static lookup (no injection path), and entity-scoping via `recordId` is correct — cross-entity activity cannot leak.

The two warnings concern a **timezone correctness bug** in the per-day bucketing (which can silently drop counts on a non-UTC server) and a **theoretical cross-table recordId collision** in the entity-scoping model. Neither is a security leak, but the timezone bug can produce a wrong sparkline. The remaining items are minor quality notes.

The pre-existing `build:analyze` route-type error (DEF-25-01) is out of scope and not flagged.

## Warnings

### WR-01: `activityCounts` day-bucketing mixes local-time and UTC — counts can be dropped on a non-UTC server

**File:** `src/server/trpc/routers/dashboard.ts:222-273`

`windowStart` is computed with `windowStart.setHours(0, 0, 0, 0)` — `setHours` operates in the **server's local timezone**. Bucket keys are then derived two different ways that only agree when the server runs in UTC:

1. The dense map keys come from `d.toISOString().slice(0, 10)` — a **UTC** calendar date.
2. The SQL groups by `to_char(date_trunc('day', ${activityLog.createdAt}), 'YYYY-MM-DD')` — `date_trunc('day', ...)` truncates in the **Postgres session timezone** (UTC on Neon), producing a **UTC** day label.

`windowStart` itself is local-midnight. When the server is not in UTC, `windowStart.toISOString()` is a non-midnight UTC instant, and the 30 keys generated by `setDate(d.getDate() + i)` + `toISOString().slice(0,10)` can be offset by one day relative to the SQL labels. Any `grouped` row whose `row.day` is not in the `buckets` map is silently discarded by the `if (buckets.has(row.day))` guard (line 267) — so real activity vanishes from the sparkline total, and the window boundary (`gte(createdAt, windowStart.toISOString())`) can include/exclude the wrong day.

This passes the test suite only because `tests/trpc/dashboard.test.ts` seeds rows at `setUTCHours(12,...)` (noon UTC) — noon is far enough from any boundary that a few hours of offset does not change the day, and Bun's test runner / CI likely runs in UTC. It will misbehave on a non-UTC deployment or for activity timestamps near local midnight.

**Fix:** Pick one timezone consistently. Simplest is to do everything in UTC:

```ts
// Window start: UTC midnight, (days - 1) days ago.
const windowStart = new Date()
windowStart.setUTCHours(0, 0, 0, 0)
windowStart.setUTCDate(windowStart.getUTCDate() - (days - 1))

// ...build buckets...
for (let i = 0; i < days; i++) {
    const d = new Date(windowStart)
    d.setUTCDate(d.getUTCDate() + i)
    buckets.set(d.toISOString().slice(0, 10), 0)
}
```

And pin the SQL truncation to UTC so it cannot follow the DB session timezone:

```ts
day: sql<string>`to_char(date_trunc('day', ${activityLog.createdAt} AT TIME ZONE 'UTC'), 'YYYY-MM-DD')`,
// ...and the matching groupBy:
.groupBy(sql`date_trunc('day', ${activityLog.createdAt} AT TIME ZONE 'UTC')`)
```

### WR-02: `activityCounts` entity-scoping by `recordId` alone is vulnerable to cross-table id collisions

**File:** `src/server/trpc/routers/dashboard.ts:231-263`

Entity scoping collects `sourceTable.id` values and filters `activityLog` with `and(eq(activityLog.tableName, tableName), inArray(activityLog.recordId, recordIds), ...)`. This is correct for the *requested* `tableName` and does not leak across entities for that table.

However `activityLog.recordId` is a bare `text` id with no entity dimension, and ids are per-table identity sequences — `bank_account` id `5` and `beneficiary` id `5` both stringify to `"5"`. The query is only safe because the `eq(activityLog.tableName, tableName)` predicate is also applied. That predicate is load-bearing for correctness, not just a filter — if a future refactor ever drops it (e.g. to aggregate "all activity for an entity"), the `recordId` `inArray` would match unrelated rows from other tables. The current code is correct; this is a fragility note. The safety of the whole scheme rests entirely on the `tableName` equality, which is not obvious from the comment block (lines 197-212 describe `recordId` scoping but do not state that `tableName` equality is what prevents cross-table matches).

**Fix:** No functional change required. Strengthen the doc comment so the dependency is explicit, e.g.:

```ts
// activity_log.recordId is a bare per-table id (text) with no entity or
// table dimension. Cross-table collisions (bank_account #5 vs beneficiary
// #5) are prevented ONLY by the eq(activityLog.tableName, tableName)
// predicate below — it must never be removed.
```

If broader aggregation is ever needed, scope on the composite `(tableName, recordId)` pair rather than `recordId` alone.

## Info

### IN-01: `activityCounts` issues an unconditional source-table scan even when the entity has no rows

**File:** `src/server/trpc/routers/dashboard.ts:232-247`

The first query (`select id from sourceTable where entityId = ...`) always runs. When `recordIds` is empty the second query is correctly skipped, but the first scan still executes on every call. For the `/accounts` sparkline this is a single indexed lookup so the cost is negligible — noting only for completeness. No change needed.

### IN-02: `bankActivity` count read is fine under React Compiler, but the empty-series fallback is subtly redundant

**File:** `src/app/(admin)/accounts/_components/AccountsClient.tsx:297-310`

`activitySeries` is derived from `bankActivity` (stable query data) and is safe under React Compiler. The KPI builds `value: activitySeries.reduce(...)` and `sparklineSeries: activitySeries.length > 0 ? activitySeries : undefined`. Because `activityCounts` always returns a dense `days`-length array (never empty when `entityId` is set), `activitySeries.length > 0` is only false before the query resolves — the sparkline simply will not render until data loads, which is the intended behavior. No bug; noting that the `length > 0` guard is effectively a loading guard, not an empty-data guard.

### IN-03: `getBeneficiariesWithDistributions` `entityId` remains optional — `sortIndex` ordering is global when omitted

**File:** `db/queries.ts:69-87`

`entityId` is optional (`entityId?: number`); when omitted the `where` is `undefined` and the function returns *all* beneficiaries across all entities, now ordered by `asc(b.sortIndex)` globally. Since `sortIndex` is only unique-ish *within* an entity (positions 0..n per entity), a cross-entity call interleaves entities by shared positions. The sole tRPC caller (`beneficiary.listWithDistributions`) always passes `entityId`, so this is not currently reachable in a broken state — noting for callers that might use the helper directly. No change needed for this phase.
