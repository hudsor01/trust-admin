<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Migration runner → production Neon DB | DDL crosses into the live database; an unaudited migration can corrupt RLS or apply with wrong column identifiers |
| Sync script → test-branch DB | The `isProductionDb` guard is the boundary keeping test-branch DDL from running against production |
| document/valuation polymorphic FK | A row may reference at most one asset; the CHECK constraint enforces this structural invariant at the DB level |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-01 | Tampering | Migration apply path (`db:deploy` vs `db:push`) | mitigate | Migration applied only with `bun run db:deploy`; `db:push` is forbidden because it corrupts RLS policies on this schema (CLAUDE.md) |
| T-28-02 | Tampering | `document` / `valuation` single-owner CHECK constraints | mitigate | The migration rebuilds both CHECKs with the `firearmId` term (9-FK and 7-FK sums); Task 2 probes that a 2-FK `document` insert is still rejected |
| T-28-04 | Elevation of Privilege | `firearm` table RLS (V4 Access Control) | mitigate | The migration emits `ENABLE ROW LEVEL SECURITY` + 4 `app.is_admin()` policies; Task 2 verifies `relrowsecurity=true` and exactly 4 policy rows — a silent failure here would leave the table world-readable |
| T-28-05 | Elevation of Privilege | Test-branch sync script run against production | mitigate | The `isProductionDb` guard (copied verbatim from `apply-0013-testbranch.ts`) refuses to run against the pooled production URL unless `ALLOW_PRODUCTION_DB` is explicitly set |
| T-28-SC | Tampering | npm package installs | accept | No package-manager installs in this phase — `drizzle-kit` and `postgres` already pinned in the lockfile; no supply-chain surface |
</threat_model>
