## Decisions for the Planner

One real visual contract gap discovered during research — not in CONTEXT.md:

### KpiStrip skeleton count (DECISION REQUIRED)

`src/components/kpi-strip.tsx` lines 22-31 hardcode `Array.from({ length: 4 })` and `lg:grid-cols-4` in the loading skeleton. After adding the 5th KPI, the loaded state renders 5 tiles across a 4-column grid (the 5th wraps to a second row on `lg`). The loading skeleton shows only 4.

**Options:**

| Option | Change | Visual consistency |
|--------|--------|--------------------|
| A (recommended) | Update `KpiStrip` skeleton to `length: data.length` + `lg:grid-cols-5` when 5 items are passed | Skeleton matches loaded state exactly — preferred |
| B | Update only skeleton count to 5, keep `lg:grid-cols-4` skeleton grid | Skeleton tiles are slightly wider than loaded tiles — mismatch |
| C | Leave skeleton at 4 | Skeleton shows one fewer tile than loaded state — visible jump |

Recommendation: Option A — pass `count` prop to `KpiStrip` or derive it from `data.length` in the skeleton path. Change is surgical (2 lines in `kpi-strip.tsx`). The Beneficiaries page is the only 5-item consumer; all other callers remain on 4 items with their existing grid.

**If the planner chooses Option A:** add a task to update `kpi-strip.tsx` before the `BeneficiariesClient.tsx` edit so the loading state is correct from first render.

**If the planner chooses Option C (do nothing):** note as a known cosmetic gap in the plan summary.
