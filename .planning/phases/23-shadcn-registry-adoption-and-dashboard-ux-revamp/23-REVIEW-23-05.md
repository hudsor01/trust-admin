# Phase 23 (slice 23-05): Code Review Report — Asset-Creation Wizard

**Reviewed:** 2026-05-19
**Depth:** deep (cross-file: traced `useResourceForm` callers + payload flow into tRPC mutations)
**Files Reviewed:** 13
**Status:** issues_found

## Summary

The 23-05 asset-creation wizard slice is well-constructed. The `useResourceForm` extension is genuinely backwards-compatible: when `steps` is omitted, `hasWizard` is `false`, all nav callbacks become inert no-ops, and the return shape adds new keys without changing existing ones — verified by tracing the 6 non-wizard callers (`Contact`, `Bequests`, `Hems`, `Settings`, `Trustees`, `Accounting`), none of which read the new fields. The payload-parity design is sound: `WizardStepGroup` toggles only a `hidden` attribute so every TanStack `Field` stays mounted, the wizard never strips keys, and `onSubmit` always submits `formInstance.state.values` whole — the same object the single-page path submits. The vendored Dice UI stepper uses only OKLCH/token classes (`bg-primary`, `border-muted`, `text-destructive`) — no theme violations.

No critical issues. The findings below are correctness gaps and quality concerns — the most material are the **edit-mode wizard regression** (WR-01), the **submit-bypass of unvisited required steps** (WR-02), and the **stale-closure risk in `isStepValid`** (WR-03).

## Warnings

### WR-01: Edit mode resets the wizard to step 0 with no completed steps — existing records become un-navigable forward only by re-validating each step

**File:** `src/hooks/use-resource-form.ts:159-164` (`handleEdit`)

`handleEdit` calls `resetWizard()`, which sets `currentStep = 0` and `completedSteps = new Set()`. For an *edit* of a fully-populated record, the user is dropped on step 1 with `completedSteps` empty. In `ResourceDialog`, `StepperItem` receives `disabled={!done.has(index) && index !== currentStep}` — so steps 2 and 3 render disabled, and `goToStep` rejects any jump to a non-completed step. The user must click "Next" through each step sequentially even though every field is already valid. This is a UX regression versus the old single-page edit form, where all fields were visible at once.

It is *functionally* recoverable (Next still works because the schemas pass on already-filled data), but it is a degraded edit experience and was likely not intended. The 7 dialogs all show `submitLabel={isEditing ? 'Save' : 'Create'}` implying edit is a supported path through the wizard.

**Fix:** In `handleEdit`, when `steps` is present, pre-populate `completedSteps` for steps whose schema already passes (or all steps), so edit lands on step 0 with full free-jump enabled:
```ts
const handleEdit = (item: T) => {
    setEditing(item)
    formInstance.reset(item)
    if (steps && steps.length > 0) {
        const done = new Set<number>()
        steps.forEach((_, i) => { if (isStepValid(i)) done.add(i) })
        setCompletedSteps(done)
    } else {
        setCompletedSteps(new Set())
    }
    setCurrentStep(0)
    setIsOpen(true)
}
```
Note `isStepValid` reads `formInstance.state.values` synchronously after `reset` — verify TanStack applies `reset` synchronously, otherwise compute validity from `item` directly.

### WR-02: A required field living in an unvisited later step can be empty at submit time — the wizard's step gating does not cover the final submit

**File:** `src/components/resource-dialog.tsx:130-145`, `src/hooks/use-resource-form.ts:96-123`

Step gating only runs in `goNext`. The submit button (`onSubmit`) is rendered whenever `isLastStep` is true. `isLastStep` is computed purely from `currentStep >= steps.length - 1` — it does **not** require that earlier steps were completed. Combined with WR-01's edit path (which lands on step 0 of an edit), or any future `open(defaults)` that seeds a later step, a user who reaches the last step without `goNext`-gating every prior step can submit with a required step-1/step-2 field blank.

In practice today the *create* flow is safe because the only way to reach step 3 is `goNext` from step 1 → 2 → 3, each gated. But the safety is incidental, not enforced. The mitigating factor is that `*.create` tRPC procedures re-validate the full payload server-side (per the file header comment and threat model T-23-PR-E-01) — so this is a UX failure (a 500/400 from the server, or a Zod error toast) rather than a data-integrity hole. Still, it contradicts the slice's stated goal that step schemas "gate" creation.

**Fix:** Gate the final submit button on all prior steps being valid, not just `isLastStep`:
```ts
// in ResourceDialog, when isWizard:
const allPriorValid = steps.every((_, i) => i >= currentStep || done.has(i))
// submit button: disabled={isLoading || (isWizard && !allPriorValid)}
```
Or have `handleSave` itself short-circuit: run `isStepValid` across every step before calling `formInstance.handleSubmit()`, and on failure jump `currentStep` to the first invalid step.

### WR-03: `isStepValid` is called on every render with `currentStep` and reads live form state — risk of stale validity under React Compiler memoization

**File:** `src/hooks/use-resource-form.ts:77-89`; consumers e.g. `src/app/(admin)/vehicles/_components/VehicleDialog.tsx:64`

`isStepValid` is a `useCallback` whose dependency array is `[steps, formInstance]`. `formInstance` is a stable reference from `useForm` — it never changes identity even as `formInstance.state.values` mutates. So `isStepValid` itself never gets a new identity. The 7 dialogs call `wizard.isStepValid(currentStep)` inline during render to compute the `isStepValid` prop passed to `ResourceDialog`, which gates the Next button.

This works **only because** the dialogs re-render when the user types (TanStack `Field` subscriptions trigger re-renders of the field, and the Select/Input `onChange` → `handleChange` propagates). But `isStepValid` reading `formInstance.state.values` is exactly the "component reads mutable state off a stable prop" pattern the React Compiler can mis-memoize: the compiler may treat `wizard.isStepValid(currentStep)` as a pure call over stable inputs (`isStepValid` identity stable, `currentStep` unchanged) and cache the previous result, so the Next button can stay disabled after the field becomes valid (or stay enabled after it becomes invalid) until an unrelated re-render.

The wizard-mode tests in `resource-dialog.test.tsx` only exercise the *hook* directly via `renderHook` and pass a *literal* `isStepValid` boolean to `ResourceDialog` — they never exercise the live `wizard.isStepValid(currentStep)` call path inside a dialog. So this gap is untested.

**Fix:** Make step validity reactive. Either (a) subscribe to form state via `formInstance.useStore`/`Subscribe` so the value is a real reactive read, and expose `isStepValid` as a derived value (not a function); or (b) wrap the Next button's gating in a `<formInstance.Subscribe selector={...}>` inside `ResourceDialog` so the compiler sees a genuine reactive dependency. At minimum, add a component-level test that types into a wizard dialog field and asserts the Next button enables.

### WR-04: Wizard `goNext` validates against per-step Zod schemas that are structurally weaker than the real create payload — invalid data passes the gate

**File:** `src/lib/asset-wizard-steps.ts` (all 7 configs), cross-referenced with `db/validation.ts` semantics in CLAUDE.md

Each step `schema` uses `nonEmpty = z.string().min(1)` for required fields and omits everything else. This is intentional per the file header, but it means the gate is satisfied by data the server will reject:

- **Money fields** (`dodValue`, `acquisitionCost`, `coverageAmount`, `premium`, `monthlyRent`, `costBasis`) are not in any step schema at all, so a user can type `"abc"` or `"12.999"` into a money input and `goNext` still advances. CLAUDE.md and the prior 23 review require 2-decimal enforcement; the wizard surfaces that error only at final submit.
- **Vehicle `vin`** is gated by `nonEmpty` only — a 3-character VIN passes step 1. The VIN input enforces uppercase but not the 17-char length.
- **Vehicle `year`** is a `number` in the form shape but appears in step 1's `fields` list with no schema entry; the field's `onBlur` clamps `< 1900` to the current year, so it is effectively always valid — acceptable, but undocumented.

This is a *quality* gap, not a bug: the server re-validates (T-23-PR-E-01). But the slice's premise — "a user cannot advance past an incomplete step" — overstates what the schemas actually enforce. Either tighten the step schemas to mirror `db/validation.ts` (preferred — money regex, VIN length), or downgrade the header comment's claim.

### WR-05: `WizardStepGroup` uses `hidden` to hide inactive steps — hidden required fields remain focusable targets for native browser validation and screen-reader/tab traversal is inconsistent

**File:** `src/components/wizard-step-group.tsx:28`

`<div hidden={!isActive}>` sets the HTML `hidden` attribute, which does remove the subtree from layout and from the tab order in modern browsers — that part is fine and is the right call for payload parity. However:

1. Several inputs in step 1 carry no `required` attribute but are visually marked `*` (e.g. `vin`, `make`). That is consistent with the form using Zod not native validation, so no native-validation trap — acceptable.
2. The `Select` components from Radix inside a `hidden` ancestor: Radix `Select` portals its content to `document.body`. The trigger is hidden correctly, but if a step transition happens while a Select dropdown is open, the portalled listbox can briefly outlive its hidden trigger. Low probability, but worth a manual QA pass on rapid Next-clicks.
3. `aria-hidden` is not set on the wrapper — `hidden` implies it for AT, so this is fine.

This is the lowest-severity warning; flagged mainly so the Radix-portal interaction (item 2) gets one manual QA pass. No code change strictly required.

## Info

### IN-01: `isStepValid` is exposed twice in the hook return with different shapes across the boundary

**File:** `src/hooks/use-resource-form.ts:198`, `src/components/resource-dialog.tsx:42`

The hook returns `isStepValid` as a *function* `(index: number) => boolean`. `ResourceDialog` accepts a prop also named `isStepValid` but typed as a *boolean*. The dialogs bridge this by calling `wizard.isStepValid(currentStep)` — correct, but the name collision (function vs boolean, same identifier) is a readability trap for the next maintainer. Consider renaming the hook export to `getStepValidity` or the prop to `currentStepValid`.

### IN-02: Seven near-identical `wizard` prop `Pick<...>` type blocks are copy-pasted

**File:** all 7 dialog files (e.g. `VehicleDialog.tsx:32-40`)

Every dialog repeats the same `Pick<UseResourceFormReturn<T>, 'currentStep' | 'completedSteps' | 'isStepValid' | 'goNext' | 'goPrev' | 'goToStep'>`. Extract a shared generic type, e.g. `export type ResourceWizardProps<T> = Pick<UseResourceFormReturn<T>, ...>` in `use-resource-form.ts`, and import it. Reduces drift if the wizard surface changes.

### IN-03: `formInstance.Field as unknown as ...` double-cast repeated in every dialog

**File:** all 7 dialog files (e.g. `HomesteadDialog.tsx:75-79`)

`NameDescriptionFields` receives `formInstance.Field` via `as unknown as Parameters<typeof NameDescriptionFields>[0]['Field']`. The `as unknown as` double-cast defeats type checking at a real API boundary — if `NameDescriptionFields`'s `Field` contract changes, no dialog will fail to compile. Consider making `NameDescriptionFields` generic over the form type, or exporting a properly-typed `Field` adapter, so the cast can be removed.

### IN-04: `WizardStep<T>` `schema` is typed `ZodType` (untyped) while `fields` is `Array<keyof T>` — schema keys are not checked against `T`

**File:** `src/hooks/use-resource-form.ts:12-21`, `src/lib/asset-wizard-steps.ts`

`schema?: ZodType` is an opaque Zod type with no relationship to `T`. Nothing prevents a step `schema` from validating a key that is not in `fields` or not in `T` at all. `isStepValid` builds its `subset` only from `step.fields`, so a schema key absent from `fields` would silently always be `undefined` and could make a step un-passable. Today the configs are correct, but a typo (`carier` vs `carrier`) would not be caught at compile time. Consider `schema?: ZodType<Partial<Pick<T, ...>>>` or a runtime dev-mode assert that every schema key is in `fields`.

### IN-05: Insurance step grouping — `premiumFrequency` and the linkage fields are correctly placed; one minor inconsistency in step labels

**File:** `src/lib/asset-wizard-steps.ts:284-322`

Field-coverage audit of all 7 configs vs their form shapes: **every form key lands in exactly one step, none dropped, none duplicated.** Verified `insurancePolicyFormDefaults` (15 keys) → step1 `name,description,policyType,carrier,policyNumber` + step2 `coverageAmount,premium,premiumFrequency` + step3 `effectiveDate,expirationDate,insuredAsset,beneficiaries,status,notes` = 14 keys; the 15th is `description`, present in step1 — total 15, complete. Same check passes for vehicle (18 keys), bank (12), investment (12), personal-property (12), homestead (`HomesteadFormData`, 12), rental (`RentalFormData`, 17).

Minor: the insurance step 2 `id` is `'valuation'` but its `label` is `'Coverage'` — the id/label mismatch is intentional (the deviation comment explains it) but the stale `id: 'valuation'` for a non-valuation step is mildly confusing. Cosmetic only; `id` is just a stepper key. Consider `id: 'coverage'` for clarity.

### IN-06: `HomesteadFormData` / `RentalFormData` are hand-maintained interfaces parallel to `homesteadFormDefaults` / `rentalPropertyFormDefaults` — drift risk

**File:** `src/app/(admin)/properties/_components/constants.ts:7-42`, vs `src/lib/form-factory.ts:112-153`

The property dialogs use `HomesteadFormData`/`RentalFormData` from page constants, while the wizard step config file imports those same types. But `form-factory.ts` *also* defines `homesteadFormDefaults`/`rentalPropertyFormDefaults` with a *different* shape (they include `propertyType`, `yearBuilt`, `squareFeet`, `bedrooms`, `bathrooms`, `units` — fields absent from `HomesteadFormData`). The `asset-wizard-steps.ts` header comment documents this deliberately. Not a bug — the homestead/rental dialogs genuinely use the slimmer page-constants shape — but two divergent "homestead form" shapes in the codebase is a latent maintenance hazard. Out of scope for 23-05 to fix; noted so it is on record.

## Cross-File Verification Notes (deep pass)

- **Backwards compatibility — CONFIRMED SAFE.** Traced all 13 `useResourceForm` import sites. Six are non-wizard (`Contacts`, `Bequests`, `Hems`, `Settings`, `Trustees`, `Accounting`) and call `useResourceForm` without `steps`. With `steps` undefined: `stepCount=0`, `hasWizard=false`, `currentStep` returned as literal `0`, `isFirstStep`/`isLastStep` both `true`, `goNext`/`goPrev`/`goToStep` early-return. The return object only *adds* keys (`steps`, `currentStep`, `isFirstStep`, `isLastStep`, `goNext`, `goPrev`, `goToStep`, `completedSteps`, `isStepValid`) — no existing key (`isOpen`, `open`, `close`, `isEditing`, `editing`, `handleEdit`, `handleAdd`, `handleSave`, `isSubmitting`, `formInstance`) changed type or semantics. Non-wizard `ResourceDialog` callers (e.g. `ContactDialog`) pass no `steps` prop → `isWizard=false` → no stepper, original footer. Test (a) covers this.

- **Payload parity — CONFIRMED, with the WR-02 caveat.** `WizardStepGroup` toggles only `hidden`; all `formInstance.Field` children stay mounted across step changes, so `formInstance.state.values` always carries every key. `onSubmit` in each client builds its tRPC payload from the full `data` object. Wizard adds no transform. Test (g) asserts byte-equality for one synthetic form. The remaining risk is not *shape* but *completeness* (WR-02): the wizard does not guarantee a later-step required field was filled, it only guarantees the key exists.

- **OKLCH/theme — CLEAN.** `stepper.tsx` and the dialog footer use only token classes (`bg-primary`, `border-muted`, `text-muted-foreground`, `text-destructive`, `ring-ring`). No hex, no `hsl()`, no raw Tailwind palette literals. The `text-red-500` literals in the dialog field error messages are *pre-existing* (present before 23-05 in the single-page forms) and outside this slice's diff — not flagged here, but worth a separate cleanup pass against the OKLCH rule.

- **`goToStep` free-jump rule — CORRECT.** `goToStep` rejects any index not in `completedSteps` (and not the current step). Test (f) covers it. Combined with `StepperItem disabled` gating, the stepper trigger for an unvisited step is also disabled, so the `onClick` → `goToStep` path is doubly guarded.
